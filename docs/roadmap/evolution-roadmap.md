# DX Artifacts evolution roadmap

## 1. Principles

DX Artifacts evolves from imported, evidenced carrier behavior toward the artifact-system vision. Each phase preserves established behavior unless a separately accepted and gated change authorizes a difference.

## 2. Controlling sequence

```text
New repository authority
→ candidate import
→ cross-repository baseline acceptance
→ package boundary
→ behavior-preserving decomposition
→ envelope read
→ envelope write
→ CLI integration
→ reports and capabilities
→ stdout-default compatibility activation
→ consumer-ready distribution
→ independent external consumer adoption
→ advanced artifact system
```

## 3. Stage 0: New repository authority

Establish DX Artifacts documentation, identities, provenance, native ownership, and external boundaries. Add no implementation behavior.

## 4. Stage 1: Candidate import

Import the Dx.Domain release-gate candidate without semantic rewriting and preserve executable historical behavior behind temporary and native entry points.

## 5. Stage 2: Cross-repository baseline acceptance

Evaluate applicable Dx.Domain and Collab evidence, classify every difference, resolve mandatory findings, and establish controlling carrier fixtures.

## 6. Stage 3: Package boundary and decomposition

Establish the `dx_artifacts` package, `dx` CLI adapter, module entry point, internal dependency direction, spooling, sinks, and typed verification without changing accepted behavior.

## 7. Stage 4: Envelope read

Add bounded envelope parsing, safe archive inspection, integrity verification, and exact carrier recovery.

## 8. Stage 5: Envelope write

Add deterministic `canonical-v1` production and golden output evidence.

## 9. Stage 6: CLI integration

Add standalone transforms and integrated envelope production through the same package behavior.

## 10. Stage 7: Reports and capabilities

Add explicit operation reports and truthful machine-readable capability discovery.

## 11. Stage 8: Stdout-default compatibility activation

Activate ADR-002 only after its compatibility gate passes. Before this stage, omitted-`-o` behavior remains the accepted bootstrap behavior.

## 12. Stage 9: Consumer-ready distribution

Produce versioned installable and standalone forms with release provenance, digests, conformance evidence, and compatibility policy.

## 13. Stage 10: External consumer adoption

Dx.Domain and Collab may independently adopt pinned releases while retaining repository-specific orchestration, policy, adapters, and integration evidence. Consumer adoption does not belong to native package decomposition.

## 14. Stage 11: Controlled application, trust, and advanced artifacts

Potential separately specified evolution includes mutation planning, preconditions, transactional application, receipts, signatures, attestations, content-addressed storage, chunked transport, and additional artifact types.

## 15. Release gates

A stage is complete only when normative behavior is documented, implementation and documentation agree, positive and negative evidence exists, deterministic output is demonstrated where required, unsafe inputs fail closed, public options are enforced, and no established behavior is unintentionally weakened.
