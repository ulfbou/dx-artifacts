# DX test fixture architecture

## 1. Purpose

Fixtures provide durable byte-level evidence for carrier preservation, envelope determinism, safety, and CLI composition.

## 2. Fixture classes

```text
fixtures/
├── carriers/
│   ├── source/
│   ├── golden/
│   └── invalid/
├── envelopes/
│   ├── golden/
│   ├── structurally-invalid/
│   ├── integrity-invalid/
│   ├── noncanonical/
│   └── unsafe-zip/
├── reports/
└── manifests/
```

This structure is conceptual. Repository conventions determine final paths.

## 3. Golden fixtures

Golden fixtures are immutable expected bytes committed with a manifest containing:

- fixture identifier;
- media type;
- format or profile version;
- byte size;
- SHA-256;
- purpose;
- producing test case;
- review status.

Golden bytes are read as binary. Tests must not normalize line endings.

## 4. Generated fixtures

Generated fixtures exercise variable sizes and combinations but are not substitutes for golden bytes.

Generators must be deterministic from an explicit seed and must record the seed in failure diagnostics.

## 5. Carrier matrix

Carrier fixtures cover:

- no trailing newline;
- one and multiple trailing newlines;
- empty file;
- directive-like content;
- UTF-8 non-ASCII content;
- CRLF and binary content represented through carrier Base64;
- read-only entries;
- multiple sorted paths;
- maximum safe path and attribute boundaries.

## 6. Envelope matrix

For each accepted carrier fixture, preserve:

- original carrier bytes;
- canonical ZIP bytes;
- canonical Base64 payload;
- complete canonical envelope bytes;
- expected layer sizes and SHA-256 values.

## 7. Invalid fixtures

Invalid fixtures each isolate one primary failure whenever practical. Their manifest records the expected diagnostic code, failed layer, and exit category.

Mutation-based invalid fixtures start from a golden artifact and alter one declared property or byte range.

## 8. Unsafe ZIP fixtures

Unsafe archives cover:

- path traversal;
- absolute paths;
- multiple entries;
- directory entries;
- symlinks;
- nonregular Unix modes;
- encryption flags;
- comments and forbidden extra fields;
- unsupported compression;
- central/local header disagreement;
- concatenated archive data;
- excessive compression ratio.

They are never extracted to a directory during tests.

## 9. Fixture provenance

Every binary fixture is either:

- generated by a repository script whose inputs are committed;
- manually constructed with documented rationale and independently reviewed.

Fixtures from untrusted external archives are forbidden unless provenance and safety review are recorded.

## 10. Fixture-change gate

A golden change requires:

- explicit scope identifying the changed contract;
- old and new size and digest evidence;
- semantic explanation;
- confirmation that unchanged fixtures remain byte-identical;
- profile version change when canonical output changes incompatibly.

Bulk fixture regeneration without an explained contract change fails the gate.

## 11. Bootstrap and consumer evidence

Before envelope fixtures control product evolution, DX Artifacts preserves the accepted root `dx.py` through native characterization and controlling golden carrier fixtures. These fixtures record source provenance, accepted implementation identity, purpose, byte size, SHA-256, and applicable behavior.

Collab fixtures remain attributed compatibility and regression evidence evaluated against the accepted baseline. They may establish obligations that must be classified and resolved before affected extraction or compatibility work proceeds, but they neither select nor revoke the baseline. Later consumer repositories retain their own integration suites; those suites do not become native implementation ownership.
